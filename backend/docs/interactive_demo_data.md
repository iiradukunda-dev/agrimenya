# Interactive demo database

The demo seeder creates synthetic records so a team can explore Agri-Menya without using real farmer, field, or NISR records. **Use a dedicated Supabase demo project. Never run it against production or a database with real users.** The script reads only `backend/.env.demo`; it does not fall back to the backend's normal `.env`.

## What it creates

The deterministic seed covers 18 demo zones across six districts; 360 synthetic crop and season metrics; demo predictions and alignment records; plans, draft alerts, readiness and work records; field observations; community demo accounts, posts, comments, and a moderation report; and opt-out WhatsApp contacts, subscriptions, inbound mock message logs, and draft templates. Synthetic season labels, text, account names, and model versions include a demo marker.

It deliberately does not add rows to `nisr_imports` or `nisr_yield_records`, does not create WhatsApp opt-ins or send messages, and does not create fake farmer phone numbers. Demo output is for interface and workflow exploration, not agricultural advice or model evaluation. Keep the demo database separate so its synthetic `agri_metrics` cannot be mistaken for NISR records.

## Set up the isolated project

1. Create a separate Supabase project for the demo. Do not reuse the production project or its service key.
2. Apply `app/db/schema.sql` and the required migrations in order through `0013_zone_identity_and_retrieval.sql` in the Supabase SQL editor. The project must include the community, field observation, WhatsApp, and zone identity tables.
3. Copy `backend/demo.env.example` to `backend/.env.demo`. Fill in both demo Supabase variables and the runtime `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` with that same demo project. Set a private random `USER_API_KEY` and `JWT_SECRET`. This file is ignored by Git.
4. From `backend/`, install the existing backend requirements, then run:

   ```powershell
   python -m scripts.seed_demo_data
   ```

   The script checks the project ref against the URL and asks you to type `SEED_AGRI_MENYA_DEMO` before writing. Re-running it upserts the same stable IDs instead of creating duplicates.
5. Point the local frontend at the API started with `backend/.env.demo`. In `frontend/.env`, set `API_BASE_URL=http://localhost:8000`, copy the same demo `USER_API_KEY`, and set `AGRI_MENYA_DEMO_MODE=true` so every page shows a persistent demo warning. Start the API with `uvicorn app.main:app --env-file .env.demo --reload` from `backend/`, then start Streamlit from `frontend/`. Keep the normal API process and production credentials separate.

## Demo sign-ins

The seed creates isolated sample accounts for the community and admin sign-in flows. They all use the same demo-only password:

- Community: `demo.farmer01@example.invalid` through `demo.farmer08@example.invalid`
- Admin: `demo.admin@example.invalid`
- Password: `DemoOnly-Agri-Menya-2026!`

These credentials are intentionally public and must never be seeded into a real environment. The API still needs a valid demo `JWT_SECRET` for sessions.

## Remove the generated rows

After ensuring the API and seeder are still configured for the isolated demo project, run:

```powershell
python -m scripts.seed_demo_data --reset
```

It prompts for the same confirmation and removes only the deterministic demo IDs and template keys generated by this script. For a complete clean reset, deleting and recreating the demo Supabase project is simpler.
